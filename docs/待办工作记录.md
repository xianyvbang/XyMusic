## 10. JVM 端数据目录改为平台标准用户目录

**目标**：把 JVM 端数据根目录从「安装盘盘符根目录 + `XyMusicData`」改为各平台约定的用户数据目录，避免落到只读位置，也避免与安装路径绑定。

**现状**：

- [ContextWrapper.jvm.kt](file:///D:/androidPro/XyMusic/xy-platform/src/jvmMain/kotlin/cn/xybbz/platform/ContextWrapper.jvm.kt#L62-L69) 的 `resolveDataDirectory()` 当前取 `installationDirectory.toPath().root`（即安装盘盘符根目录）再拼 `${appName}Data`，在本机表现为 `D:\XyMusicData`。
- 数据库、缓存、临时、下载目录都从 `dataDirectory` 派生：`database`、`cache`、`temp`、`Downloads/XyMusic`。
- 盘符根目录（尤其是 `C:\`）普通用户通常无写权限，MSI 安装到 `C:\Program Files\` 后该方案会直接建库失败。
- 已有覆盖入口：系统属性 `cn.xybbz.dataRoot`（`DATA_ROOT_PROPERTY`），可指定任意数据根目录。
- 相关测试：[ContextWrapperJvmTest.kt](file:///D:/androidPro/XyMusic/xy-platform/src/jvmTest/kotlin/cn/xybbz/platform/ContextWrapperJvmTest.kt#L16-L37) 断言了默认路径为盘符根目录，改动后需同步更新。

**通用做法（各平台约定）**：

| 平台 | 配置/数据 | 缓存 | 用户可见文件 |
| --- | --- | --- | --- |
| Windows | `%APPDATA%\XyMusic`（Roaming）或 `%LOCALAPPDATA%\XyMusic` | `%LOCALAPPDATA%\XyMusic\Cache` | `%USERPROFILE%\Music\XyMusic` |
| macOS | `~/Library/Application Support/XyMusic` | `~/Library/Caches/XyMusic` | `~/Music/XyMusic` |
| Linux | `~/.local/share/XyMusic` | `~/.cache/XyMusic` | `~/Music/XyMusic` |

- Roaming 会随域账户漫游同步，只适合小而重要的配置；数据库、缓存等大体积数据必须放 Local，否则会拖慢登录同步。
- 主流桌面应用参考：Electron 默认 `%APPDATA%\<产品名>`；Chrome、VS Code 把大体积数据放 `%LOCALAPPDATA%`；JetBrains IDE 配置放 Roaming、缓存放 Local。

**建议的目录映射**：

| 现有目录 | 建议改为 |
| --- | --- |
| `dataDirectory/database` | `%LOCALAPPDATA%\XyMusic\database` |
| `dataDirectory/cache` | `%LOCALAPPDATA%\XyMusic\cache` |
| `dataDirectory/temp` | `%LOCALAPPDATA%\XyMusic\temp` |
| `dataDirectory/Downloads/XyMusic` | `%USERPROFILE%\Music\XyMusic`（或保留 `Downloads\XyMusic`） |

**要点**：

- 修改 `resolveDataDirectory()`：优先级为「`cn.xybbz.dataRoot` 覆盖属性 > 平台标准用户数据目录」。
  - Windows 取 `System.getenv("LOCALAPPDATA")`；macOS/Linux 取 `System.getenv("XDG_DATA_HOME")`，为空时回退 `~/Library/Application Support` 或 `~/.local/share`。
  - 最终目录为 `<用户数据目录>/<appName>`，与现有 `appName` 解析保持一致。
- 保留 `cn.xybbz.dataRoot` 覆盖能力，绿色版/便携版可用它把数据固定到安装目录旁（`-Dcn.xybbz.dataRoot=<安装目录>`），无需改代码。
- 不采用「默认放安装目录」方案：jpackage MSI 默认装到 `C:\Program Files\XyMusic\`，普通用户启动时无写权限，数据库、缓存、临时文件都会失败；如需兼顾绿色版，可加「安装目录可写则用之，否则回退用户目录」的探测逻辑。
- 老数据迁移：数据库路径变化后，`D:\XyMusicData` 中的歌单、播放记录、下载记录会被视为新安装。需要加一次性迁移逻辑，把旧目录下的 `database`、`cache`、`temp` 搬到新目录；迁移完成打标记，避免重复执行；迁移失败时保留旧目录并给出提示，不阻塞启动。
- 同步更新 `ContextWrapperJvmTest` 的默认路径断言，并补一条「`cn.xybbz.dataRoot` 覆盖时所有子目录从覆盖目录派生」的用例（已有 `dataRootPropertyOverridesRuntimeDriveRoot` 可复用）。
- 校验：全新安装后数据落在用户数据目录；`cn.xybbz.dataRoot` 覆盖生效；老版本升级后歌单/播放记录/下载记录仍在；`C:\Program Files` 安装场景下建库成功。

        ?: dataSourceManager.restoreLocalDataSourceContext()
        ?: state.value.connection
        ?: return
    // 交互式登录可能发生在临时对象上；若当前发布的服务尚未初始化，

## 12. 交互式登录成功后精确回传本次 `ConnectionConfig`，去掉「最新创建连接」兜底

**目标**：登录成功后，会话要用的连接配置必须是**本次登录写入的那一条**，不再依赖 `settings.connectionId` + 「按创建时间取最新」来猜。

**现状**：

- `loginAfter` 的临时对象分支只做 `connectionState.updateConnection()`，不写 `settings.connectionId`（[IDataSourceParentServer.kt#L331-L360](file:///D:/androidPro/XyMusic/composeApp/src/commonMain/kotlin/cn/xybbz/api/client/IDataSourceParentServer.kt#L331-L360)）；正式分支的 `connection()` 才会 `saveConnectionId`（[#L1494-L1501](file:///D:/androidPro/XyMusic/composeApp/src/commonMain/kotlin/cn/xybbz/api/client/IDataSourceParentServer.kt#L1494-L1501)）。
- `markInteractiveLoginSuccess()` 无参调用时走 `restoreLocalDataSourceContext()`：先读 `settings.connectionId`，匹配不上就 `selectConnectionConfigOrderByCreateTime()` 取最新创建（[DataSourceManager.kt#L208-L225](file:///D:/androidPro/XyMusic/composeApp/src/commonMain/kotlin/cn/xybbz/api/client/DataSourceManager.kt#L208-L225)）。
- `ClientLoginInfoState.UserLoginSuccess` 是无载荷状态（object），[ConnectionViewModel#L303-L318](file:///D:/androidPro/XyMusic/composeApp/src/commonMain/kotlin/cn/xybbz/viewmodel/ConnectionViewModel.kt#L303-L318) 拿不到本次保存的配置，只能让 SessionCoordinator 再查一遍库。
- 多连接场景下「最新创建」不等于「本次登录」：新增连接时是最新，更新已有连接时会指向其它新建连接，会话切错。

**要点**：

- 首选方案：让 `loginAfter` 把 `savedConnectionConfig` 往上抛（作为 flow 载荷或 `addClientAndLogin` 的返回值），由 `DataSourceManager.addClientAndLogin` 记录到 `lastLoginConnectionConfig`（`var` 或 `StateFlow<ConnectionConfig?>` 均可），避免事后查库。
- 次选方案（改动小、仍有并发风险）：`DataSourceManager` 在收集到 `UserLoginSuccess` 时查库记录最近一次配置；不建议继续用「最新创建」在 SessionCoordinator 里兜底。
- `ConnectionViewModel` 登录成功回调改为 `sessionCoordinator.markInteractiveLoginSuccess(dataSourceManager.lastLoginConnectionConfig)`，与第 11 项改动 2 的守卫配合。
- 保持「临时对象不写 `settings.connectionId`」的语义不变：探测不应污染全局设置，配置只作为结果交给调用方决定是否切换。
- 若选择把 `UserLoginSuccess` 改成 `data class(val connectionConfig: ConnectionConfig?)`：需同步 `getLoginSateInfo` 的 `when` 分支（加 `is`）与所有引用点（`grep "UserLoginSuccess"` 全量核对）。
- 新增字段/方法补中文注释。

**校验**：

- 已有连接 A 正常使用 → 新增连接 B 成功 → 当前会话、首页数据、设置里的当前连接都必须是 B。
- 更新已有连接（id 不变）后登录成功 → 当前连接仍是该 id，不会跳到「最新创建」的其它连接。
- 清空数据库后重新登录、connectionId 被复用场景仍能进入 Ready 并触发首页刷新。
- `grep "UserLoginSuccess"` 结果全部已同步（若改了状态类型）。

## 13. `switchDataSource` 替换旧数据源前先关闭旧服务，避免连接池与协程作用域泄漏

**目标**：每次切换当前数据源时，旧服务必须被释放，不再出现「对象被丢弃但 HttpClient 连接池、IoScoped scope、TokenServer 全局数据留在内存里」。

**现状**：

- `switchDataSource()` 只做 `updateDataSourceType` + `getDataSourceServerByType` + 发布，旧服务既不 `close()` 也不 `release()`（[DataSourceManager.kt#L432-L458](file:///D:/androidPro/XyMusic/composeApp/src/commonMain/kotlin/cn/xybbz/api/client/DataSourceManager.kt#L432-L458)）。
- 只有 `DataSourceManager.release()` 会关闭当前服务（[#L1509-L1518](file:///D:/androidPro/XyMusic/composeApp/src/commonMain/kotlin/cn/xybbz/api/client/DataSourceManager.kt#L1509-L1518)）。
- `IDataSourceParentServer.close()` 会 `defaultParentApiClient.release()` + `TokenServer.clearAllData()` + `unConnection()` + `sendLoginCompleted(UNKNOWN)`（[IDataSourceParentServer.kt#L1655-L1660](file:///D:/androidPro/XyMusic/composeApp/src/commonMain/kotlin/cn/xybbz/api/client/IDataSourceParentServer.kt#L1655-L1660)）；`DefaultApiClient.release()` 已负责 `httpClient.close()`（[DefaultApiClient.kt#L345-L350](file:///D:/androidPro/XyMusic/api/src/commonMain/kotlin/cn/xybbz/api/client/DefaultApiClient.kt#L345-L350)），各数据源子类的 `release()` 也都会 `super.release()`，释放能力已具备，只是切换路径没调用。
- 结果：每次「连接管理里切换连接」「新增连接生效」「从临时对象回退到正式服务」都会留下一个旧服务及其 HttpClient 连接池和协程作用域。

**要点**：

- `switchDataSource()` 中先取 `old = currentDataSourceServerOrNull()`；发布新服务后，若 `old != null && old !== new` 则 `old.close()`。
  - 顺序建议「先发布新服务、再关旧的」，避免 `_dataSourceServerFlow` 出现短暂 null 导致 UI/会话读到空态。
  - 同类型 + 同连接 ID 的早退分支不做关闭，保持现状。
  - `close()` 内部会 `TokenServer.clearAllData()`：正常路径下 `switchDataSource` 之后都会紧接登录（`initApiClient` 会重建 TokenServer 数据）；但若存在「切换后不登录就直接 Ready」的路径（即第 11 项修复的那个缺陷），这里会暴露成鉴权失败而不是崩溃，属于可接受的降级，不要为了兼容而跳过关闭。
- `release()` 可复用同一段「关闭当前服务」逻辑，避免两处写法不一致。
- `close()` 是同步方法，不要在其中引入 suspend 调用；需要挂起的清理放到各自 scope 内。
- 注意不要让关闭动作取消正在进行的登录 flow：仅关闭「已被新对象替换」的旧服务，不关闭本次正在使用的服务。

**校验**：

- 反复切换连接 / 反复新增连接若干次后，HttpClient 实例数量与协程作用域不增长（调试日志或内存观察 `close` 调用次数与对象数量）。
- 切换后首页、播放、图片与音频流地址均正常（TokenServer 已由新连接的登录流程写入）。
- `release()` / 删除最后一个连接仍能完整释放，无「关闭两次」异常。
- 不主动执行 Gradle 编译。
